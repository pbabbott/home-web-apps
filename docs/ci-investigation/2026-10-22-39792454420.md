## Headline: the install layer is now cached

In all three Next.js base builds the `pnpm install --frozen-lockfile` layer was **`CACHED`**, as were `npm install pnpm turbo`, the `store-dir` config, the lockfile/workspace copies, and `COPY out/full`. Cache import worked in every case (`inferred cache manifest type: application/vnd.oci.image.manifest.v1+json`, no `not found`).

| `pnpm install --frozen-lockfile`                | CACHED | CACHED         | CACHED        | 4m 13s / 7m 48s             |
| `turbo build` (`#19`)                           | 91 s   | 207 s          | 95 s          | 22 s / 11 s                 |

So the layer cache did what it was meant to for the first install, which was 4–8 min in attempt 2. It did not fix the build, because the work after it still runs.

## Why the steps after the cache hit still run (likely cause, not proven by experiment)

`docker/pnpm-turbo.Dockerfile` sets, in the `development` stage before `turbo build`:

```
ARG IMAGE_TAG=""
ENV IMAGE_TAG=${IMAGE_TAG}
...
COPY --from=pruner /app/out/full .
RUN ... turbo build ...
```

The build passes `--build-arg IMAGE_TAG=20261022-208-049a0ef`, which differs on every run (date, run number, SHA). `ENV` changes the environment seen by every later `RUN`, so the `turbo build` layer (`#19`) is not reusable. The `builder` stage then wipes `node_modules` and reinstalls with `--prod`, and `#20`–`#22` follow from `#19`, so they re-run too. Consistent with this: `#18` (`COPY`, no env dependency) was `CACHED` and `#19` was not.

Two consequences:

- The `--prod` install depends only on the lockfile, but it is stacked after a layer that changes on every commit, so it never hits the cache.
- The app's own turbo task logged `cache miss, executing` this time. In attempt 2 (same commit as attempt 1) it replayed from the remote cache and ran in 11–22 s. The new `IMAGE_TAG` reaching turbo's environment hash is a plausible reason; I did not check turbo's inputs.

I have not tested a Dockerfile change. These are observations from one run.

The same step again varies 4–9× between runs (`--prod` install: 1–2 min in attempt 2, up to 9.4 min here; `exporting layers` 52 s to 651 s). That is the contention signature seen in earlier runs, not a property of the image.

## Cache export cost (answers an earlier open question, partly)

The `mode=max` registry cache export is not free on the base images: **68.6 s for blog's base**, 4.3 s for the lighter final image in attempt 3. For `diagram-maker` it was still running at the timeout. So on a slow build it competes with the timeout, while on a fast build it is small. One run; the earlier "little support" view of this theory is weaker than I stated in the previous note.

## What this adds

- **The registry layer cache works** for the Dockerfile's first `pnpm install`, in all three Next.js apps, and cache import is reliable. That removes 4–8 min per app compared with attempt 2.
- **It is not enough on its own**, because `IMAGE_TAG` (probably) invalidates `turbo build` and, behind it, the `--prod` install, which took up to 9.4 min on a contended disk.
- **The disk tail, not the repo, decides whether the heavy builds finish.** Same layers, 4–9× variation in the same steps.
