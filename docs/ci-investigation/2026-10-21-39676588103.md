# CI cold run analysis: run 39676588103 (PR #223)

First run of `chore/ci-improvements` (PR #223). It is deliberately a **cold** run: the `ts-jest` catalog bump changed `pnpm-lock.yaml`, so every lockfile-keyed cache missed. Goal of this doc: explain _why_ a cold run is slow, with evidence for a hardware purchase decision. Builds on [2026-10-21-39665721971.md](./2026-10-21-39665721971.md).

- **Run:** `39676588103` (workflow run #207), 21:10:23 → 22:09:19 UTC, **58 min 56 s, failed**.
- **Result:** 3 of 12 `docker-build` jobs failed (blog, diagram-maker, home-hud). Everything else passed. Security, integration, smoke and preview jobs were skipped because of the failures.
- **Sources:** `gh` job/step data and logs; Prometheus (`https://prometheus.local.abbottland.io`) for 21:10–22:10 UTC; the Proxmox host (`192.168.4.192`) and the three prod workers (`192.168.6.25–27`).

## Failing docker builds

| Job             | Result  | Job time | `Publish SHA-tagged image` | Where the 20-min budget went                                                                  |
| --------------- | ------- | -------- | -------------------------- | --------------------------------------------------------------------------------------------- |
| `blog`          | failure | 23m 23s  | timed out after 20 min     | `exporting layers` 419.8 s, then push, then `exporting cache to registry` was still running   |
| `diagram-maker` | failure | 25m 03s  | timed out after 20 min     | `exporting layers` 451.2 s, then push, then `exporting cache to registry` was still running   |
| `home-hud`      | failure | 25m 06s  | timed out after 20 min     | `exporting layers` still running after 6m 42s when the timeout fired. The push never started. |

All three are the large Next.js `builder` images. The step has `timeout-minutes: 20` (`.github/workflows/ci.yml`), and none of them finished inside it.

Rough phase budget for a cold Next.js image build (from the three logs):

| Phase                                         | Duration                                           |
| --------------------------------------------- | -------------------------------------------------- |
| Base image pulls + `pnpm install` (cold)      | 3.5 – 5.7 min                                      |
| `turbo build`                                 | 1.5 – 2.7 min                                      |
| Second `pnpm install --prod` (after cleanup)  | 2.6 – 5.7 min                                      |
| `exporting layers` (write image to dind disk) | **7.0 – 7.5 min** (home-hud: >6.7 min, unfinished) |
| Push + registry cache export                  | did not complete                                   |

Findings:

- **These builds were already borderline.** In run 39665721971, `home-hud` also timed out at 20 min and `diagram-maker` failed on attempt 1 and only passed on attempt 2, as a 24-minute job. `blog` failed early on ELDERWAND (cause not examined). This run is not clearly a regression from PR #223; it is the same builds failing again on a colder path.
- **The 7-minute layer export is a disk write.** The builder image is written into dind's local `/var/lib/docker`, which sits on the saturated NVMe (see below).
- **Possible extra cost from our own change.** `buildCache` adds `--cache-to type=registry,mode=max`, which runs _after_ the push. In blog and diagram-maker the cache export was in flight when the timeout hit. We cannot separate this from the disk cost with one run. See "Open questions".
- **Not a Dockerfile logic error.** The `Dynamic server usage` lines in the home-hud log are expected build-time warnings, not the failure.

## Why the cold path is slow

### 1. The first stage stalls on a cache stampede (17 min before `build` could start)

Five jobs run in parallel with the same lockfile-keyed `node_modules` cache key: `lint`, `format`, `unit-test-plan`, `docker-build-plan`, `integration-test-plan`. All missed the cache and all did a full install at once. Previous run, same stage: ~4 min. This run:

| Job                                           | Duration    |
| --------------------------------------------- | ----------- |
| `lint`                                        | 1000 s      |
| `unit-test-plan`                              | 868 s       |
| `integration-test-plan` / `docker-build-plan` | 644 / 642 s |
| `format`                                      | 527 s       |

Timeline of `lint`:

| Time (UTC)          | Event                                                                                                                                                          |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 21:10:52            | `Cache not found` for `Linux-node-modules-b54ca142...`                                                                                                         |
| 21:12:30            | `pnpm install --offline` fails: `ERR_PNPM_NO_OFFLINE_TARBALL` (new `ts-jest` not in the NFS store)                                                             |
| 21:12:30 → 21:20:28 | Fallback `pnpm install`: `reused 1714, downloaded 2, added 1728`. **~8 min**, almost all from the store, so it is linking/copying small files, not downloading |
| 21:20:28 → 21:27:10 | Post step: save the 328 MB cache. **6 min 42 s**                                                                                                               |
| 21:27:15            | `build` finally starts                                                                                                                                         |

`format` and `unit-test-plan` show the same shape: install 434 s and 581 s, and a cache-save post step of 50 s and 260 s. Only `lint`, `format` and `unit-test-plan` were inspected step by step.

Two separate costs here:

- **Install:** 1,728 packages copied from the NFS-mounted pnpm store onto local disk (cross-filesystem, so no hardlinks). It is small-file write IO against the busy disk, run five-wide.
- **Cache save:** all five jobs try to save the same key. Only one can be useful. The rest burn minutes of disk and network for nothing.

### 2. The disk is saturated for almost the whole run

Proxmox host `nvme0n1` (Crucial P3 Plus 1TB, QLC, DRAM-less), 5-minute averages over the run:

| Window (UTC) | Disk busy | Write latency | Write MB/s | Worker iowait (avg of 3) | Phase                       |
| ------------ | --------- | ------------- | ---------- | ------------------------ | --------------------------- |
| 21:10        | 23%       | 6.2 ms        | 12         | 3%                       | stage 1 starts              |
| 21:15        | 88%       | 13.7 ms       | 74         | 21%                      | 5 cold installs             |
| 21:20        | **96%**   | 15.9 ms       | 34         | 39%                      | cold installs + cache saves |
| 21:25        | 89%       | 17.1 ms       | 7          | 24%                      | cache saves                 |
| 21:30        | 55%       | 4.2 ms        | 15         | 10%                      | `build` (fast)              |
| 21:35        | 65%       | 8.3 ms        | 167        | 15%                      | 12 jobs start               |
| 21:40        | 88%       | 9.1 ms        | 65         | 53%                      | docker builds + installs    |
| 21:45        | 91%       | 11.9 ms       | 43         | **62%**                  | docker builds               |
| 21:50        | 91%       | 20.6 ms       | 42         | 56%                      | image export                |
| 21:55        | 93%       | 11.2 ms       | 34         | 48%                      | image export + timeouts     |
| 22:00        | 92%       | **26.2 ms**   | **5**      | 46%                      | last builds                 |
| 22:05        | 95%       | 20.7 ms       | **5**      | 33%                      | last builds                 |

Whole run: disk busy avg **84%**, peak 97%. Worker VM disk write latency avg 42–48 ms (peak 150–247 ms). Worker IO pressure averaged ~0.5, so tasks were stalled on IO about half the time, while worker CPU user time averaged only 10–13%.

**The sharpest data point is the tail (22:00–22:10).** The disk was 92–96% busy while moving only ~5 MB/s, with ~80 read IOPS and ~150–180 write IOPS (about 250 IOPS total) and queue depth 10–12. A healthy NVMe sustains tens of thousands of IOPS and does not saturate at 5 MB/s. That pattern fits a QLC, DRAM-less drive whose SLC write cache is exhausted and which is now writing straight to slow QLC while doing background garbage collection. It is consistent with the earlier finding (run 39665721971: ~81% busy, 21 ms write latency). This is a strong hardware-limit signal, not a configuration one.

Caveat: the Proxmox host `iowait` and this device-level view cannot tell us on their own whether the drive is hitting its SLC cliff or being throttled thermally (earlier reading: 55 °C, no critical warning). A controlled benchmark would settle it (see below).

### 3. Same job, different runner

Jobs that happened to land on **ELDERWAND** (a separate self-hosted runner outside the k8s cluster; specs unknown) finished roughly 4–11× faster than the same work on `arc-runners`:

| Job                             | ELDERWAND (this run) | k8s (`arc-runners`)                     |
| ------------------------------- | -------------------- | --------------------------------------- |
| `unit-tests (video-api)`        | 68 s                 | 278 s (run 39665721971, attempt 1)      |
| `docker-build (node-22-alpine)` | 48 s                 | ~9 min (run 39665721971)                |
| `docker-build (homelab-api)`    | 186 s                | 17.8 min publish step (run 39665721971) |

Same code, same commands, so the difference is the environment, not the repo. Note: these jobs also ran against warm vs. cold caches in places, so treat the ratios as indicative. They still show the repo's work is not inherently slow.

## Evidence summary for the hardware decision

1. One consumer **QLC, DRAM-less NVMe** holds every k8s VM root disk (containerd, kubelet `emptyDir`, dind `/var/lib/docker`, runner `_work`).
2. During CI it was **84% busy on average for the hour**, with 6–26 ms average write latency and a tail at ~250 IOPS / ~5 MB/s while 95% busy.
3. Workers spent **30–60% of CPU time in iowait** and ~0.5 IO-pressure, with only 10–13% user CPU. The cluster is waiting, not computing.
4. The slowest steps are all small-file or large-layer **writes**: cold installs (1,728 packages), cache saves, `exporting layers` (7+ min).
5. The same repo work finishes several times faster on a runner outside this cluster.
6. Memory pressure was ~0 and runner CPU use averaged under one core, so more CPU or RAM alone would not fix this.

## Open questions and next measurements

- **Does `--cache-to mode=max` push builds over the timeout?** Experiment: re-run with `mode=min`, or temporarily raise the step timeout to 40 min to see the true duration of the three failing builds.
- **Is it the SLC cache cliff or thermal throttling?** Run a controlled benchmark on the Proxmox host when CI is idle: `fio` 4k random write, plus a 5-minute sustained sequential write to expose the cliff. Not run yet: it loads the shared disk, so it needs a quiet window and your OK.
- **Warm run:** re-run this PR (or push an empty commit) to measure the layer cache and the `node_modules` cache hit path against this cold run.
- **Stampede mitigation:** have only one job warm the `node_modules` cache and make the other first-stage jobs depend on it (or restore without saving).
- **Candidate drive comparison:** once a candidate NVMe is chosen, run the identical `fio` profile on it and compare against the P3 Plus numbers above.
