# CI slowness investigation — 2026-10-21

## Context

A full `ci.yml` run takes ~45–60 min, and PRs keep needing re-runs for "flaky infra". This investigation looks for the real bottleneck (CPU / memory / IO / config / hardware).

- **Runs analysed:** PR #220 (`feature/exodus-review-candidate`). Run `39650669053` (3 attempts) and run `39665721971` (2 attempts).
- **Window:** 2026-10-21 18:12–20:47 UTC.
- **Sources:** `gh` job/step timings and logs, `kubectl` (namespace `arc-runners`), Prometheus (`https://prometheus.local.abbottland.io`) and read-only `ssh root@192.168.4.192` (Proxmox).

## Verdict

1. **Disk IO is the main bottleneck.** All k8s VM root disks live on one consumer QLC, DRAM-less NVMe, and CI saturates it.
2. **CI config throws caches away on every job.** Each job repeats IO-heavy work (Node download, `node_modules` extraction, a cold `pnpm install` inside Docker, a cold turbo build).
3. **The 1-CPU container limits** on runner/dind pods throttle the work that isn't waiting on disk.

Memory, Harbor and the network are **not** the problem.

Follow-up across 19 runs, with hardware options and research tasks: [Hardware and infra bottleneck analysis](./2026-10-22-hardware-bottleneck.md). It confirms the disk as the ceiling and adds two untested contributors (online `discard` on the workers, LVM-thin zeroing).

- **Runner pod resources:**

## Plan / suggested next steps

Ranked by value for effort. Nothing below has been applied yet.

### 1. Repo-side fixes (cheap, large wins — one PR)

1. **Enable the Docker layer cache for base builds.**
   - Add `buildCache: harbor.local.abbottland.io/build-cache` to every `apps/*/abctl.base.yml`: blog, diagram-maker, home-hud, homelab-api, video-api and video-worker.
   - The existing `cacheRef` handling in `packages/abctl/src/docker-cli/docker-commands.ts` already emits the flags.
   - Expected: the Dockerfile `pnpm install` layer is `CACHED` while the lockfile doesn't change.
2. **Pass turbo remote-cache settings into the Docker build.**
   - Trace why abctl passes empty `TURBO_API`/`TURBO_TEAM` build-args (see `packages/abctl/src/build-logic/docker-build-settings-builder/`). Wire them from the job env that `scripts/turbo-auth.sh` sets.
   - Also confirm the URL: the `turbo-auth.sh` default points at the `non-prod` domain, and the nonprod VMs are stopped.
3. **Remove the dead Node cache** in `.github/actions/pnpm-setup/action.yaml` (the `~/.nvm` cache never matched where `setup-node` installs). Caching the tool-cache path would not help: the cost is disk IO, not download. Bake Node into the runner image instead (see Cluster config 3).
4. **Skip pnpm-setup where it isn't needed.** Docker-build entries like `node-22-alpine` and `node-22-dev` don't need host `node_modules`.
5. **Simplify buildx.**
   - Prefer `driver: docker`, unless registry cache export requires `docker-container`.
   - If it does, pin the buildkit image through the Harbor proxy (`driver-opts: image=...`) so it isn't pulled from Docker Hub every time.
6. **Investigate the ~2.7 min tail** after vitest in `fui-components-ui-tests` (container teardown vs. hanging browser).

### 2. Cluster config (ARC values / gitops; applied by hand)

1. **Raise or remove CPU limits.**
   - Raise runner 1 → 2–3 and dind 1 → 3, or drop CPU limits and keep requests.
   - Today most containers are throttled while the nodes sit around 13% CPU user.
2. **Reduce concurrency.**
   - Lower the docker-build `max-parallel: 6` and the ARC max runners to about 3–4 concurrent dind jobs.
   - On one QLC disk, fewer parallel jobs finish sooner and avoid timeouts.
3. **Bake tooling into the runner image.** Build a custom image with Node 22, pnpm 10.15, jq and the `op` CLI, replacing `ghcr.io/falcondev-oss/actions-runner:latest`. This removes setup-node, `npm i -g pnpm`, jq and op installs from every job.
4. **Avoid per-job Playwright image pulls.**
   - Run UI tests in a runner pod built from `playwright-runner`, instead of `docker run` inside dind.
   - Alternatively, keep a node-local image cache.
5. **Spread the shared caches.** Move `actions-cache-server` / `turborepo-remote-cache` off worker-1, or keep runners off whichever node hosts them.

### 3. Hardware (highest ceiling)

1. **Replace or supplement the P3 Plus.**
   - Use a DRAM-equipped TLC NVMe (e.g. Samsung 990 Pro, WD SN850X, Kingston KC3000) for VM root disks.
   - At minimum, add a dedicated disk for kubelet `emptyDir` / `/var/lib/docker` on the workers.
   - The 5800H has CPU headroom; the disk is the ceiling.
2. **Move `etcd-ssd` off the BX500** that it shares with Longhorn. It isn't the problem today, but it's a stability risk under Longhorn load.

## Next steps (after attempt 3)

Ordered by value for effort. Evidence: [attempt 1](./2026-10-21-39676588103.md), [attempt 2](./2026-10-22-39676588103-attempt-2.md), [attempt 3](./2026-10-22-39676588103-attempt-3.md). Nothing below has been applied yet.

1. **Decouple the `--prod` install from `IMAGE_TAG`.** Done measuring step 1 ([run 39792454420](./2026-10-22-39792454420.md)): the first install is `CACHED`, but `turbo build` and the `--prod` install re-run because `ARG/ENV IMAGE_TAG` sits before them in `docker/pnpm-turbo.Dockerfile` and changes every commit. Move it after those steps or give the `--prod` install its own lockfile-keyed stage. One change per commit, then re-run on a fresh commit.
2. **Fix the `gh-pages` push race in `fui-components-ui-tests`.** Attempt 3's push was rejected as non-fast-forward (`fetch first`) after the tests passed. Rebase or retry on push, or add a concurrency group to the deploy. Unrelated to disk speed, and it will keep failing runs.
3. **Triage `integration-tests (homelab-api)`.** It failed in attempt 3 with a foreign-key violation on `inventory_items` and several `Exceeded timeout of 5000 ms` errors, and has no baseline. Run `inventory-items.integration.test.ts` locally: if it passes quickly, the timeouts point at the slow CI disk; if the FK error reproduces, it is a test data or ordering bug.
4. **Pass the buildx builder explicitly** (`BUILDX_BUILDER` from the `setup-buildx-action` step's `name` output). The "Cache export is not supported for the docker driver" race did not fire in attempt 3, but its cause is understood. Apply after step 1 so that run stays clean.
5. **Run the controlled `fio` benchmark** on the Proxmox host in an idle window (4k random write, plus a 5-minute sustained write). The early-fast then slow-and-saturated disk pattern appeared in all three attempts; this is the evidence the hardware decision needs. It loads the shared disk, so it needs a quiet window and an OK.

Deferred: the `mode=min` and longer-timeout experiments. The one registry cache export observed cost 4.3 s (attempt 3, `diagram-maker`), so the cache-export-causes-timeouts theory has little support. Revisit only if step 1 shows slow exports.

## PromQL used (re-runnable)

Run these as `query_range` over the CI window with `step=60`.

```promql
# CPU by mode, % of node
sum by (instance,mode) (rate(node_cpu_seconds_total{mode=~"user|system|iowait|steal|softirq"}[2m]))
  / on(instance) group_left count by (instance) (node_cpu_seconds_total{mode="idle"}) * 100

# Pressure (PSI)
rate(node_pressure_io_waiting_seconds_total[2m])
rate(node_pressure_cpu_waiting_seconds_total[2m])
rate(node_pressure_memory_waiting_seconds_total[2m])

# Disk busy fraction / write latency (ms) / write MB/s / write IOPS
rate(node_disk_io_time_seconds_total{device!~"dm-.*|loop.*"}[2m])
rate(node_disk_write_time_seconds_total[2m]) / rate(node_disk_writes_completed_total[2m]) * 1000
rate(node_disk_written_bytes_total[2m]) / 1e6
rate(node_disk_writes_completed_total[2m])

# Container writes / CPU by namespace
sum by (namespace) (rate(container_fs_writes_bytes_total[2m])) / 1e6
sum by (namespace) (rate(container_cpu_usage_seconds_total{container!=""}[2m]))

# CPU throttling ratio per runner pod
sum by (pod,container) (rate(container_cpu_cfs_throttled_periods_total{namespace="arc-runners"}[2m]))
  / sum by (pod,container) (rate(container_cpu_cfs_periods_total{namespace="arc-runners"}[2m]))
```

Proxmox host is `instance="192.168.4.192:9100"` (job `node-exporter-physical`). Worker VMs are `192.168.6.25–27:9100`.
