## Observations

### 1. The Docker layer cache did nothing in this run, and why

All three Next.js base builds logged:

```
#7 importing cache manifest from harbor.local.abbottland.io/build-cache/<app>-base
#7 ERROR: failed to configure registry cache importer: .../<app>-base:latest: not found
```

and there were zero `CACHED` lines. The cache ref did not exist, because the cache is exported **at the end of the build** (`--cache-to ... mode=max`), and in attempt 1 blog, diagram-maker and home-hud timed out before that export finished. **A build that times out leaves no cache, so the slowest builds never get to benefit from the layer cache.** This run exported the cache for blog and home-hud successfully (`exporting cache to registry`, `writing layer ...`), so a third run is the first one that could show `CACHED` layers. Not yet measured.

Consequence for attempt 2: the Dockerfile `pnpm install` still ran cold.

| Step in base build                                 | blog   | home-hud   |
| -------------------------------------------------- | ------ | ---------- |
| `pnpm install` (cold)                              | 4m 13s | **7m 48s** |
| `pnpm install --prod`                              | 1m 08s | 2m 05s     |
| `turbo build` (remote cache hits for dependencies) | 22 s   | 11 s       |

`home-hud`'s install took 7m 48s here versus 3m 30s in attempt 1, for the same lockfile. That is the same step, same inputs, 2× apart, which fits disk contention (see 3) rather than anything in the repo.

### 2. Turbo remote cache works, and image export got much faster

- Logs show `Remote caching enabled` and `cache hit, replaying logs` for the dependency packages. The app's own `#19` build step ran in 11–22 s.
- `exporting layers`, the 7-minute step that killed attempt 1, took **52 s (blog)** and **73 s (home-hud)** this time, for the same images. Pushing took 8.5 s and 12.8 s.
- The disk was **not quiet** while these ran: the 5-minute bucket around the exports had the NVMe 95% busy with ~39 ms write latency (below). So "the disk was idle this time" does not explain it. Fewer simultaneous heavy writers is the likeliest explanation (at export time roughly 3 k8s builds were running, versus about 5 in attempt 1), but I have not proven it. Treat the cold 420–450 s as a contention outcome, not a fixed cost of the image.

Whole attempt: disk busy avg **80%** (peak 96%), write latency avg 22.5 ms (peak 51.6 ms), worker IO pressure avg 0.5.

Two patterns worth keeping as hardware evidence:

- **Throughput falls as the run goes on.** At the start the drive delivered 95–121 MB/s and 1.9–2.6k IOPS at 10–13 ms. Twenty minutes later it delivered 25–41 MB/s and 750–870 IOPS at 35–39 ms, at ≥93% busy, with fewer runners (7 versus 11). That is what a QLC drive does when its fast write cache fills. It also matches attempt 1's tail (~5 MB/s while 95% busy). The drive had been idle for ~1.5 h before this attempt, so the early numbers show roughly its best case.
- **Even the best case is modest.** About 2.6k write IOPS at 10 ms is far below what a DRAM-equipped TLC NVMe sustains.

### 4. The `diagram-maker` failure is a separate, non-timeout problem

It failed in 4 min, on **ELDERWAND-2**, with:

```
ERROR: Cache export is not supported for the docker driver.
```

What the logs show:

- Its base build ran on the `docker-container` builder `builder-a8d8c665...` (log: `building with "builder-a8d8..." instance using docker-container driver`).
- The next build, the final image, ran without that builder: the error means it used the default `docker` driver.
- `docker info` inside the job reports `Name: ELDERWAND` although the runner is `ELDERWAND-2`, so the two ELDERWAND runners appear to share one Docker daemon (and one buildx config).
- Concurrently on ELDERWAND, `docker-build (homelab-api)` created its own builder, then ran `docker buildx rm` on it at 23:51:55. `diagram-maker`'s final build started at 23:52:20.

**Likely cause (consistent with timing, not proven):** `setup-buildx-action` creates its builder with `--use`, which sets the shared "current builder". When a concurrent job on the same Docker host removes its own builder, the shared current builder falls back to the default `docker` driver, and any later `docker buildx build` without an explicit builder fails on `--cache-to`. This is a race between two concurrent jobs on one host. It only appears when two docker-build jobs overlap on the same ELDERWAND host.

This predates PR #223: `buildCache` was already set on the final image builds. It just happened to hit this time.

Possible fix (not applied): pass the builder explicitly, e.g. set `BUILDX_BUILDER` from the `setup-buildx-action` step's `name` output in the publish step's `env`, so each job always uses its own builder.

### 5. Work that does not benefit from caching is still slow on k8s

- `fui-components-ui-tests`: 649 s warm vs 559 s cold. `blog-ui-tests`: 504 s on k8s vs 222 s when it ran on ELDERWAND in attempt 1. Caches don't help these; they are Playwright running in a 1-CPU dind pod on the shared disk.
- `Setup pnpm and Node.js` is still 86–146 s on the k8s docker-build jobs (versus 20 s on ELDERWAND). The cost is `setup-node`'s copy into the tool cache on the busy disk.

### 6. `video-worker` is not a clean data point

It finished in 201 s versus 1249 s cold, but its log shows the `docker manifest inspect` existence check for `video-worker-base:sha-61de1e4`, and attempt 1 had already pushed that image. It likely skipped most of the build. Don't count it as a caching win.

### 7. Scheduling luck changes the picture

14 of 31 jobs landed on ELDERWAND this time, so k8s had less concurrent work than in attempt 1. That makes this attempt flatter than a fully loaded k8s run, and it is another reason the cold-to-warm numbers above should be read as indicative.

## What this adds to the hardware case

- Concurrency alone doesn't explain the slowness: even with half the jobs on ELDERWAND and 5–11 runner pods, the NVMe sat at 72–96% busy, and worker iowait was 33–52%.
- The drive degrades within one run (95–121 MB/s down to 25–41 MB/s), which a controlled sustained-write benchmark should reproduce.
- The same step can vary 2–8× between runs (`pnpm install` 3.5 vs 7.8 min, `exporting layers` 7 min vs 52 s), a sign of shared-resource contention.
