## Observations

### 1. The `pnpm install` layer-cache question is still open

Zero `CACHED` lines in any docker-build log, and zero base builds ran. In `blog`, `home-hud` and `diagram-maker` the base-image publish step logged:

```
Image harbor.local.abbottland.io/library/<app>-base:sha-61de1e4 exists in the remote registry.
Nothing to do. Skipping push.
```

`blog` and `home-hud` skipped their **final** image too (`<app>:sha-61de1e4` already existed from attempt 2), which is why those jobs took 181 s and 138 s: setup plus a `docker manifest inspect`. **These are not caching wins.** The SHA-tagged existence check makes a re-run of the same commit skip the build, so a re-run of this commit can never exercise the Dockerfile layer cache for the base images.

To measure it, the commit must change (an empty commit gives a new SHA tag), while `pnpm-lock.yaml` and the Dockerfile stay unchanged so the install layer is still valid. Not yet done.

Cache import status, from the one build that did run (`diagram-maker` final image):

- `importing cache manifest from harbor.local.abbottland.io/build-cache/diagram-maker` **succeeded** (`inferred cache manifest type: application/vnd.oci.image.manifest.v1+json`, 0.2 s). Attempt 2's note said this cache had never been exported. The ref exists now, but I did not establish which run wrote it. Unproven.
- The final image has only `FROM base` plus copy steps, so there was no install layer in it to hit. It did not show `CACHED` for any step.

Cache export was cheap here: 4.3 s, overlapping the push. The earlier concern that `--cache-to mode=max` pushes builds past the timeout is **not supported by this build**. It is one data point, and the layers were mostly already in the registry.

The slow parts were pulling an existing base image from Harbor and the Node setup step. Both are reads or writes to the busy disk. Neither is the image export that dominated attempt 1.

### 3. The buildx "Cache export is not supported for the docker driver" race did not recur

The race needs two docker-build jobs overlapping on one ELDERWAND host, and it did not happen to line up here. **That is absence of the trigger, not evidence of a fix**: the explicit-builder change is not applied.

### 5. `fui-components-ui-tests` failed on a git race, not on disk

It ran on ELDERWAND, passed its tests, and failed at the very end pushing to `gh-pages`:

```

error: failed to push some refs to 'github.com/pbabbott/home-web-apps.git'
```

Another workflow pushed to `gh-pages` at the same time, and the push was rejected as non-fast-forward. This is a separate problem from performance. Which other job pushed was not examined. It passed in attempts 1 and 2, so it is intermittent.

### 6. `integration-tests (homelab-api)` failed; cause not established

It ran 834 s on k8s and failed in two suites:

- `inventory-items.integration.test.ts` (173 s): `POST /queue-items/:id/inventory-items failed: DrizzleQueryError` with `violates foreign key constraint "inventory_items_source_id_sources_id_fk"`.
- `discovery.integration.test.ts` (127 s): several `Exceeded timeout of 5000 ms for a test.`

Also seen earlier in the same log: `Error: Get "http://%2Fvar%2Frun%2Fdocker.sock/v1.55/containers/buildx_buildkit_..._/json": context deadline exceeded`, when the builder booted. That one did not fail the job on its own.

I did not determine whether these are a slow-disk symptom (the 5000 ms timeouts would fit a slow Postgres on a 98%-busy disk) or a real test bug (a foreign-key failure points at test data or ordering). **Unproven either way.** This job never ran in attempts 1 or 2, because earlier failures skipped it, so there is no baseline for it.

## What this adds

- **The same-commit re-run limits what a re-run can show.** Blog and home-hud skip the whole build when `<app>:sha-<commit>` exists, so only a new commit measures the layer cache. Skipped builds should not be counted as speedups (as with `video-worker` in attempt 2).
- **Disk behaviour reproduced across attempts 2 and 3**: 80% busy average, latency 22–24 ms average, the same early-best then slower pattern, and a 63 ms worst bucket. The stage-3 integration tests, new in this attempt, had the worst bucket.
- **Cache export cost looks small** (4.3 s for `diagram-maker`), from one build.
- The slow steps on k8s that remain are reads and writes of existing data: `Setup pnpm and Node.js` 335 s, base-image pull 325 s, `COPY` 76 s.
